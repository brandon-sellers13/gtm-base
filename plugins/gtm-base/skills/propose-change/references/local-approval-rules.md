# Approving a prepared change on a base with no shared copy

A base with no shared copy has nowhere to send a proposed change, so the owner
approves it here instead. These are the rules that path follows, in plain
words, so nobody has to read the code to know what it will and will not do.

## When this path runs at all

It runs only when the base has no shared copy. A base that has one keeps the
path that already ships, where the change is raised for review and somebody on
the team reads it there. Asked on a base with a shared copy, this path says so
in one sentence and points at the other one. When that question cannot be
answered at all, because the base's own settings could not be read for a
moment, the run stops and says so rather than treating the base as one without
a shared copy.

Nothing about what may leave the computer changes here. Nothing is sent, and
the two conditions that hold everything back are neither asked nor altered,
because there is nothing for them to hold back.

## The person is the step

The showing and the yes are two separate runs on purpose, and the permission
prompt in front of the second one is the step this whole design rests on. They
must never happen in the same turn: the owner reads the change, and then the
owner answers. For the same reason the script that applies a change must never
be put on a list of commands that run without being asked about. A yes nobody
stopped to give is not a yes.

## The order it happens in

1. The prepared change is read, and only from the folder GTM Base keeps
   prepared changes waiting in. A file anywhere else is never read as one, and
   is never moved or thrown away as one either.
2. Every path it names is checked. It may only touch your context files, the
   record of context changes, and the record of what was corrected, and it may
   never touch the assistant's own folder. The path an edit names also has to
   be the file it really is, so a link inside the context folder, or the same
   name written in different letters, can never quietly point an edit at your
   base's map.
3. The change it carries and the marker that names it have to agree, because
   the line recording your yes names that change, and a change nobody could
   name would leave the document flagged against the very thing you approved.
4. A change already recorded here is refused rather than applied twice.
5. It is checked against the files as they read right now, by applying every
   edit to a copy held in memory. When the part it rewrites is not there any
   more, or the file itself is gone, the run says so, applies nothing, and
   offers to have the change prepared again.
6. Everything it carries is read for things that must never leave a computer:
   contact details, keys, web addresses carrying a key, and text a reader would
   not see. That includes the headings it names, which get written into the
   file, and the note the work is saved under. Anything found stops the run,
   and the reason names the kind of thing found and never the thing itself.
   This runs here, on a base with nothing to send, because the first backup
   turns this copy into the shared copy.
7. The whole change is written out: the four labeled lines, then the context
   change it carries exactly as it will be written down, then every part of
   every file it touches as that part reads now and as the change would leave
   it. Two edits to one file are shown one after the other, each against the
   answer the one before it gave.
8. One thing is asked. Approve it, leave it for now, or drop it.

## What the yes is bound to

The showing hands back one value that stands for exactly what was read: the
prepared change itself and the current text of every file it touches, each
piece counted so that two different readings can never add up to the same
value. The yes carries that value back. If either half moved in between,
nothing is applied and the change is shown again, because a yes about words
that have since changed is an answer to a different question.

## Who may approve

Only an owner of every file the change touches. The owner is the address
written on the file, and who is answering is the address this base records work
under, which is the same rule a confirmation is recorded under. Anybody else is
refused and told which address owns the file.

That rule is there to stop an honest mistake, such as a second person on a
shared machine approving something about a document that is not theirs. It is
not a defence against somebody who means harm: anybody who can edit this base
can also change the address it records work under. The real protection is that
nothing here can reach anywhere off the computer.

## What a yes writes

One piece of saved work holds all of it together, so the base can never hold a
changed file that nobody approved:

- every file the change rewrites,
- the context change it carries, when it carries one, written only when the
  base does not already hold it,
- one line per file recording the owner's yes, because an owner accepting a
  change is that owner saying the file is right,
- the record of what changed, which is what says later that this was accepted,
  and which the four-week numbers count exactly as they count a change accepted
  on a shared copy.

The prepared change is then filed away as the copy it can be raised from again.
Your base has to have nothing unsaved in it first, and it has to be on its main
line.

## What leaving it for now, and dropping it, do

Leaving it for now writes nothing anywhere and leaves the prepared change where
it was waiting. Dropping it moves the prepared change into the folder of ones
nobody wanted. It is moved rather than deleted, for two reasons: nothing here
ever deletes a file outright, and the next check has to be able to tell that
this change was already decided about, so tomorrow it does not prepare the same
one all over again. Either way the document it was about is left exactly as it
was, and it stays flagged.

## What a run that stops halfway does

Before anything is written, a note of what this run is about to write is left
in this account's own folder, outside the base. The note names each path
together with the exact content this run will put there. The next run reads
that note as data and checks every value in it: the paths have to be ones this
path writes to, they have to stay inside this base, and the note has to say it
is about this base at all. A note that fails any of that stops the run and
nothing is touched.

Work that was already saved is finished off, whatever else has been saved
since. Work that was not saved is undone, and a path is only undone when what
is on the disk is exactly what that run was going to write there. A path
holding your own words instead is left exactly as you left it, and the run
stops and asks you to deal with it. A path that could not be put back keeps the
note, so the run can always be finished later. Either way the base ends in the
same state it would have ended in had nothing gone wrong, and it never holds
half of a change.

## What this path does not do

Listing every open proposal from a shared copy, turning one down while keeping
the context change behind it, and checking a proposal against what the reviewer
saw on the shared copy are all the other half of reviewing proposals. They
arrive with backup, and they are not here.
